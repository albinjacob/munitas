Feature walkthrough

Munitas
A data platform that can prove what happened to your data.

Munitas is an open-source platform that runs on a single machine. It keeps a permanent record of every dataset, every pipeline step that touched it, and every AI agent that read it. Each claim on this page is checked by an automated script that runs against the live system, so nothing here rests on a promise. Two example organisations, health and finance, run throughout this page and the guided walkthroughs in section 13, for illustration.

01 · What it does

It governs AI agents with the same rules it applies to data

Most data platforms carefully track datasets and stop there. The AI agents that read those datasets are treated as ordinary software: deployed, changed, and rerun with no permanent record of which version did what.

Munitas closes that gap. An agent is registered and given sealed, numbered versions, exactly like a dataset. When it runs, it gets an identity assigned by the system it runs inside, not by anything the AI model itself can read or write. That means a malicious instruction hidden in a document cannot change what the agent is permitted to do.

One worked example agent ships with the platform. It ranks the queue of transcripts waiting for a human to check, so reviewers start with the riskiest rather than the first in the list. Section 10 explains the job in full, including how it has to ask a custodian for access before it can read that queue at all.

Specifically, the platform can:

  • Lock a dataset version so nobody can alter it afterwards. The database itself blocks the change, so a bug in the application cannot bypass it.
  • Make data available to a wider audience without copying or moving any files. Changing who may read a version only changes which access credential unlocks it.
  • Run a seven-step pipeline that strips personal information out of audio recordings, then put the result in front of a named reviewer, with every identifier it measured as still left behind, before anything is released more widely.
  • Pause an agent partway through a run and hold it there until a person approves it. The pause survives a restart, so approval can come days later.
  • Record every decision to allow or refuse access, along with the reason, so the history can be read back later.
  • Delete a person's records permanently without rewriting any locked dataset, by destroying the encryption key that record depends on.
  • Require a real sign-in through Ory Kratos before anyone can act, rather than letting the console take someone's word for who they are.
  • Store each organisation's data in its own isolated bucket, and on Cloudflare R2 its own short-lived credential, so a leaked credential reaches one customer rather than all of them.
  • Let a sandboxed agent read the real dataset it was scoped to, through a copy it fetches itself over an isolated network, capped in size before a single byte moves.
  • Change who holds which role only through two people: one asks and says why, another decides, and the role lapses rather than lasting because nobody looked. The administrator who runs the platform is not one of the people who may decide.
  • Show what storage each organisation is using, on which backend, and free what is no longer needed, rehearsing exactly what would be removed before removing it.
  • Write one line of log per event carrying identifiers and never contents, with anything resembling a secret redacted before it is written.

02 · Scope

A complete system on one machine, not a scaled-down prototype of one

Every guarantee on this page is enforced by the platform running today, not described in a specification for later. Production-scale infrastructure was left out deliberately: none of it changes whether those guarantees hold.

BUILT

Registering, versioning and locking datasets. One built-in seven-step pipeline that removes personal information from speech recordings. Widening who may read a dataset. Requesting and approving access. Keeping separate customers' data apart, and closing an account without deleting its history, or deleting it permanently and completely. Registering, versioning, deploying and running AI agents, including a human approval step and, for sandboxed agents, a scoped copy of the real dataset they were granted. Permanent deletion of a person's records. A full audit trail. Importing datasets from HuggingFace in the background, using each person's own account, with export rules read from the dataset's licence. Real sign-in through Ory Kratos for every human role. A choice of storage backend per organisation, SeaweedFS or Cloudflare R2, each isolated per customer.

The goal is the one a title document serves for a property: proof of what is held, by whom, and on what terms. This platform holds that proof for a dataset, and for an AI agent and everything it did.

03 · Architecture

Every request passes the policy engine, and there is no way around it

The web console and the background worker both go through the API. Only the API talks directly to the database, the file storage and the policy engine, so there is a single place where access rules are applied. The agent runtime sits on a network of its own that has no route to the internet. That isolation is a property of how the network is configured, not a rule the code is trusted to follow. Every read the agent attempts is still checked by the policy engine, on the same terms as a person's.

04 · Core concepts

Four ideas that the rest of the system is built on

Widening access never moves the data

Every dataset version sits at one of five sensitivity levels, from RAW (most restricted) up to PUBLISHED. Moving a version up to a less restricted level changes only which access credential opens it. The files themselves are never copied or rewritten, which was confirmed by checking that their storage keys and checksums are identical before and after.

Sensitivity and origin are two separate questions

Sensitivity decides who inside the organisation may read a dataset. Its origin decides whether it may leave the organisation at all. A public benchmark and a clinical dataset with names removed can be equally safe to read internally, while only one of them may legally be published. Treating these as one setting either blocks harmless downloads or releases regulated data as soon as it looks safe enough to read.

An agent's identity is assigned, never self-declared

An agent's identity is held by the program running it and is never part of the data the AI model can see or modify. Every time the agent tries to use a tool, its permissions are rechecked against that assigned identity. This is what protects against prompt injection, where an attacker hides instructions inside a document the agent reads. Such an instruction can change what the model asks for, but it cannot change who the system believes the agent is.

Deleting a person's data without rewriting history

Each record is encrypted with its own key. To delete a record permanently, the platform destroys that key rather than editing any locked dataset. The record becomes unreadable everywhere it ever appeared, while the dataset versions and audit trail stay exactly as they were. A short marker is kept to record that the deletion happened, so the fact of the erasure is not itself erased.

05 · Proven, not promised

Every claim on this page is checked by an automated script against the live system

Nothing above is a design intention or a roadmap item stated as though it already works. Each capability is exercised by its own script, run against the real platform rather than a mock of it, covering everything from locked dataset versions and cross-customer isolation to agent sandboxing, prompt-injection resistance, and permanent, verifiable deletion. When a claim changes, the script that proves it changes with it.

06 · How it is measured

Two things are measured, for two different reasons

The pipeline that removes personal information is measured on accuracy, because the risk is that it misses something. An agent is measured on consumption, because an agent that gets stuck in a loop does not crash. It carries on working, producing reasonable-looking output and spending money. Both sets of numbers control a decision the system then makes on its own.

Removing personal information: accuracy

These figures come from comparing the pipeline's output against a known answer key. Two of them set the recommendation the reviewer is shown when deciding whether a result may be released to a wider audience. The rest are recorded to explain a poor score.

MeasureWhat it tells youUsed for
Recall after transcriptionOf the identifiers that were still readable in the transcript, the share the pipeline removed. This is the fairest measure of the pipeline's own work, because it excludes names the speech recognition had already garbled beyond recognition.Below 0.98 and the recommendation is fail
Names left fully readableIdentifying text that survived completely intact, such as a full name or an email address still in plain sight.Above 0 and the recommendation is fail
Recall against everything spokenThe same share, but measured against every identifier actually said aloud, including ones the speech recognition destroyed by accident. Always the lower of the two figures.Recorded only
Partial fragments left behindIdentifiers that were damaged but might still be pieced back together, such as a surname with two letters changed.Recorded only

Transcript accuracyHow closely the transcript matches what was actually said. This separates a pipeline that failed to redact from one that was given a bad transcript to work with.Explains a score

These numbers are stored on the decision record itself, not only in the experiment tracker, so the reason a dataset was released stays available even if the older run history is cleared out. The bar is set deliberately high, and a run that falls short is stopped and shown to a reviewer as a fail recommendation rather than released automatically.

The recommendation is advice, and the pipeline acts on none of it. It stops there and a person decides, because a threshold can only measure what the answer key already knows about, and the reviewer is looking at the identifiers that survived rather than at a number standing in for them. A pass is not a release either: an unreviewed result stays where it is until somebody signs for it.

Agent runs: consumption limits

Every run is given three ceilings. The program running the agent enforces them, rather than asking the AI model to respect them. Crossing any one stops the run immediately and records which limit was hit.

LimitDefaultWhy it exists
Tool calls per run25Caps how many times one run can reach for data or take an action
Tokens per run100,000Caps the total amount of text the model may process, which is what a stuck run consumes fastest
Seconds per run300Caps elapsed time, so a run that is waiting on something rather than looping is also stopped

Alongside these limits, each run keeps a running count of its tool calls and a full record of every access decision those calls produced. The count adds up across a pause and resume rather than restarting, so approving a paused run cannot hide what the first half already spent. An automated test confirms that a task written to loop forever stops at the tool-call limit.

07 · Value for an AI development organisation

The hard part is not storing the data. It is accounting for it afterwards.

An auditor gets an answer, not an assurance

"What did this model read, under whose authority, and who approved it" becomes a database query. Every decision to allow or refuse access was recorded at the time, together with the reason, so nobody has to reconstruct events from memory and old chat threads.

An incident can be scoped in minutes

Any suspicious output can be traced back in a single query to the exact code, software image and input data that produced it. Each agent run permanently records the version that actually ran, so deploying a newer version afterwards does not obscure what happened.

A prompt-injection attempt ends as a refusal

Because an agent's identity is held outside the model, the most a hidden instruction can achieve is to be refused and logged. There is no higher level of access for it to reach, because the permission check never reads anything the model produced.

Serious agent actions cannot skip human review

The review step is built into how the agent runs, not written down as a rule staff are expected to follow. The run stops before the significant step and can only continue once a second person approves it, and that person must belong to the same customer and must not be whoever started the run.

Publication rules keep working as data changes

Whether a dataset may leave the organisation is worked out from where it came from and what its licence permits, traced through everything that has been done to it. It does not depend on a person remembering to set a field correctly.

A leaked storage credential does not become a breach of every customer

Storage credentials are scoped to one organisation's bucket and expire quickly, rather than being one static key shared across every customer. Losing one credential exposes the blast radius it was scoped to, not the whole platform.

No licence cost, and no vendor to leave

Every component is under a permissive open-source licence, so there are no seat fees and no contract renewals. Keeping the guarantees described here does not depend on staying with any particular supplier.

08 · Cost and return

What it costs to run, and which recurring work it removes

Two things drive the return: what the platform costs to run, and which expensive manual work it removes entirely. Both are laid out below, worth checking directly against your own organisation's numbers.

Software licences: nothing

Every component is under a permissive open-source licence, so there are no per-seat charges, no per-machine governance fees and no renewals to negotiate. Replacing any one component, such as the file storage or the workflow engine, costs the effort of the integration and nothing else.

Running an agent: hardware, not usage fees

The agent's AI model runs on the machine's own graphics card instead of a paid external service. The cost of a run is therefore the cost of hardware you already own, rather than a bill that grows with every request. The per-run limits in section 6 cap how much of that hardware any single run can occupy.

Removes: reconstructing an audit trail

Answering "what did this agent read, and who approved it" is a query against records written at the time. The alternative is several people spending days piecing the answer together from logs, chat history and recollection, which also produces a less reliable answer.

Removes: tracing a bad output by hand

A suspicious result can be traced to the exact code and input data behind it in one query. Doing the same without recorded lineage means manually working out which run, which code revision and which data were involved, typically hours of work under time pressure.

Removes: arguing about whether a release was safe

The figures from section 6 and every identifier that survived are attached to the decision record, along with who accepted them and why. The judgement still belongs to a person, but it is made once, on evidence everyone can see afterwards, rather than re-argued from memory in a meeting.

Caps: the cost of an agent that gets stuck

A run that loops instead of finishing is stopped at 25 tool calls, 100,000 tokens or 300 seconds, whichever comes first. The worst case is therefore a known, small amount, rather than however long it takes someone to notice.

09 · Who uses it

Seven kinds of role, shown through one example organisation

Every organisation on Munitas is staffed by people in these same kinds of role: someone who brings data in, someone accountable for each department's data, someone who asks to read it, an administrator who runs the platform itself, and so on. The table below shows one worked example, the cast from the health organisation used throughout this page: Hartley and Okonjo each custodian a different department (Cardiology and Radiology), Devi brings data in, Sam asks to read it, Priya administers the platform, Nakamura oversees data protection, and Imani reviews what the de-identification pipeline could not confirm on its own. The finance organisation, covered in its own walkthrough, is staffed by a different cast in these same roles. Each role has a real, signed-in identity you can act as directly. "Reads by default" means the most sensitive data that role can open without anyone approving a specific request.

There are two custodians because each owns a different department, and that is the point rather than an accident of the example. Hartley can approve access to Cardiology's data and cannot approve access to Radiology's, and Okonjo the reverse. Ownership is what decides who may say yes, so a request goes to the person accountable for that particular data rather than to whoever happens to be senior or available.

Every person has the same default, including the administrator. Anything more sensitive requires a specific request that somebody else approves. Only the de-identification pipeline reads raw data, because removing personal information from raw recordings is the entire job it exists to do.

Two roles are deliberately barred from approving access requests. The data protection officer is excluded because approving access means deciding how data gets used, and GDPR Article 38(6) requires that the officer's independent oversight is not compromised in that way. The platform administrator is excluded because the account that operates the system should not also be able to grant itself access to what the system protects.

Imani decides a different question from the custodians, and only that one. A custodian decides who may read a dataset. Imani decides whether what the pipeline produced is de-identified well enough to be released more widely at all, which nobody else in the table may decide. She reads the identifiers that survived redaction, because that is the material the judgement is made on, and she reads no dataset any other member of staff could not.

10 · What each role does

What each role does, step by step

Every step below starts with signing in for real through Ory Kratos. Nothing can be approved, revoked or decided without that real, signed-in identity behind it. Each entry ends with what typically happens in an organisation that has no system like this, which is the clearest way to see what the step is for.

DeviData engineer
  1. Registers a new dataset, naming the department that owns it and where the data came from. The registration is refused if the department does not exist or the origin is left unstated.
  2. Loads the data in, either by uploading files or by importing from HuggingFace. The import runs in the background, so the screen responds immediately no matter how large the source is.
  3. Locks the version once loading has finished. The system refuses to lock it while an import is still running, so a version can never be sealed halfway through arriving.
  4. Uploads recordings for de-identification and seals them as recordings rather than as anonymous files. The platform reads each one and tells her its length and sample rate, so a truncated file is refused as she adds it instead of surfacing later. If the set is incomplete, sealing is refused with every problem listed at once and nothing is sealed.
  5. Starts the de-identification herself, from the screen she just sealed on, instead of asking whoever has a terminal on the machine that does the work. She is refused, in writing and before anything starts, if the version holds ordinary files rather than recordings, if a recording arrived without the answer key the scoring needs, or if nothing is running to do the work. A refused start leaves nothing behind to clean up.
  6. Follows the run on its own page while it happens, step by step, rather than waiting without knowing whether it is working or stuck. At the end she is told it is waiting on a reviewer, and that she cannot be that reviewer, because she is the one who started it.
  7. Does not read the sensitive data the pipeline later produces from it. Running the loading process does not grant access to the results.
  8. Starts the triage agent against the review queue the pipeline left behind. She opens the agent, picks that dataset version, and says what the run is for.
  9. Is told before she starts that the agent cannot read that data, which custodian would be asked, and that the request will be filed in her name. Nothing is asked of anybody until she confirms.
  10. Sees the run listed as waiting for data access rather than as running. It has not begun, the screen does not pretend otherwise, and it moves only when the custodian decides.
Without this: data arrives via a script somebody ran once, its origin is recorded in a wiki page if at all, and nobody can later establish whether a dataset was finalised before or after the last file landed.
HartleyCardiologyData custodian
  1. Checks claims about how sensitive a dataset is. If whoever registered it said the data is less sensitive than the cautious default, a custodian has to agree before that claim takes effect.
  2. Reviews access requests for Cardiology's datasets. Each request names a specific dataset version, what it will be used for, and why that use needs this data.
  3. Is refused if she tries to approve a request for Radiology's data, because Okonjo owns that department and she does not. Ownership is what grants the authority.
  4. Approves or refuses. She cannot approve her own request, or one somebody filed on her behalf. Both the policy engine and the database enforce this independently.
  5. Sees a written reason with every refusal, naming which rule caused it, rather than only an error code.
  6. Sees requests made for an agent in the same queue as requests made for a person, showing which agent will read the data and which engineer asked for it. Approving one starts the waiting run; refusing it closes that run with her reason attached, so nothing is left waiting on a decision that has already been made.
Without this: access is granted in a chat message, with no lasting record of who asked, what for, or what they actually received. Whoever answers first becomes the approver, regardless of whether the data was theirs to give, and the rule against approving your own request exists only on paper.
SamResearcher
  1. Requests access to one specific dataset version, stating what the work is for and why it needs that data. Blanket requests for a whole department are not possible.
  2. Waits for the custodian of the department that owns the data, who is the only person able to approve it.
  3. Asks the system for access once approved. It checks whether the role already allows this, and if not, whether an approved and still-valid grant covers it.
  4. Receives a credential limited to that dataset alone, and only after the decision has been written to the audit record.
Without this: finding out who can currently read a dataset means asking everyone who might hold a key, and access granted for a short project quietly continues working long after the project ends.
PriyaPlatform administrator
  1. Keeps the platform running: starting services, monitoring jobs and traces, and freeing up storage. She does that last one from a screen rather than from a shell: what each organisation is using, on which storage backend, what can be freed, and a rehearsal of exactly what a clean-up would remove before anything is removed.
  2. Closes a customer account when the relationship ends. From that point nothing new can be written, but everything already recorded stays readable, so the audit history outlives the contract. If a customer relationship needs to end completely rather than just close, a separate, deliberately alarming permanent-deletion path exists for that, and refuses to run against an active customer without an explicit override.
  3. Holds the most powerful account in the system, and deliberately has no standing access to the data it protects and no ability to approve access requests for anyone, including herself.
  4. Cannot change who holds which role, either. Anybody may ask to hold one and somebody else decides it, so the account that runs the system is not also the account that decides who may read what. The role that administers roles cannot be obtained from the running system at all: a second administrator is made the way the first one was, deliberately and from outside.
Without this: whoever can restart the services can usually also read everything those services protect. The account most worth attacking becomes the one with the fewest restrictions on it.
NakamuraData protection officer
  1. Reads every access decision the platform has recorded, both grants and refusals, across every department and customer she is responsible for overseeing.
  2. Reads no more of the underlying data than any other member of staff. Being able to review decisions is kept separate from being able to see what those decisions were about.
  3. Cannot approve access requests. This keeps her oversight independent of the decisions she is meant to be reviewing.
Without this: oversight depends on asking engineers to extract logs whenever a question comes up, and the person reviewing access decisions may well be one of the people making them.
ImaniDe-identification reviewer
  1. Opens a queue of finished pipeline runs waiting on a decision. Each one shows what the run scored, what the check recommends, and why it recommends it.
  2. Reads the identifiers that survived redaction, one row each: which record and which character positions it sat at, what kind of identifier it was, how much of it was removed, and how it failed. This is the material the judgement is made on, so it is shown rather than summarised into a score.
  3. Promotes the result, or holds it back. Either way she writes a reason, and neither is possible without one.
  4. Cannot decide a run she started herself. The database refuses it, not only the interface.
  5. Is the only role that may make this call. A custodian owns the data and would be judging their own department's output; an administrator operates the system and holds no standing access to what it protects; and the data protection officer is the one later asked whether the release was sound, which is not a question you can answer about your own signature.
  6. Is under no deadline, and neither is the queue. Nothing expires, escalates or promotes itself while a decision is outstanding, which is also why nothing yet chases her when one has been waiting too long.
Without this: either a threshold releases data on its own, so a number stands in for a judgement about identifiers nobody looked at, or the release is agreed informally and there is no record of who accepted the risk, on what evidence, or when.
De-identification pipelineAutomated
  1. Works through seven steps to strip personal information out of audio recordings: transcribe, identify speakers, detect identifiers, hand off for human correction, replace the identifiers, measure what was missed, and write down what it found for a reviewer to decide on.
  2. Saves its progress after each record, so a step that fails partway through resumes rather than starting the whole job again.
  3. Is the only account that reads raw, unredacted data, because removing personal information from raw recordings is exactly what it exists to do.
  4. Records whether each run was started by a person or by a schedule, so there is never any doubt about what set it off.
  5. Releases nothing, whatever it scored. Its last step records what it found and the pipeline ends there, waiting on a reviewer, whether the score passed the bar or not.
  6. Gives every step of a run the same identifier, so a run that grows into more than one workflow is still one traceable execution rather than several unrelated ones.
Without this: the job that strips personal data either cannot reach the raw recordings it needs, or is given the same broad access as everything else. There is no way to say that a process is trusted to redact data without also trusting it with everything. And the process that decides whether its own output is safe to release is the same one that produced it.
Triage agentAutomated: AI agent

The job it does. When the pipeline has finished detecting personal information in a batch of recordings, it leaves a queue of transcripts for a person to check, because a missed identifier is a leak and only a human confirmation closes that risk. The queue is normally far longer than reviewers can work through in a day. This agent reads each waiting transcript and ranks it high, normal or low with a one-line reason, so the riskiest are checked first instead of whatever happens to be at the top of the list.

A transcript in that queue looks like this, with the identifiers still in place because that is exactly what a reviewer is there to confirm:

clinician: Right. Let me pull up the notes. Eoghan Bell, born 12 February 1965, is that correct?

It produces a judgement and nothing else. It cannot release data, change anyone's permissions, or read a dataset on its own authority.

  1. Is deployed as one specific locked version, identified by the exact code it contains. Deploying a newer version while a run is in progress does not change which version that run is using.
  2. Cannot read the review queue by default. The queue holds unredacted transcripts, so it is held at the most restricted level, and this agent is trusted only with published data.
  3. Gets access the same way a person would. Starting a run against data it cannot read files a request naming the agent as the reader and the person who started the run as the one who asked. The custodian who owns that data approves it, and that approval is what sets the run going.
  4. Runs under an identity held by the surrounding program, not by the AI model. An instruction hidden in a transcript cannot change the identity its permissions are checked against.
  5. Raises any document that appears to address it to high priority, rather than doing what it says. Text aimed at the reader is itself a reason for a person to look at that document.
  6. Stops before its final step and reports that it is waiting for sign-off, rather than reporting success it has not earned. A different person accepts the findings, and the paused state is stored so that can happen days later.
  7. If it runs sandboxed rather than natively, and its version declares it needs a copy of the data, fetches that copy itself over an isolated network only after the same access decision above has been granted, capped at a fixed size before a single byte moves.
Without this: which version of the agent ran, what it read, and who let it continue past the decisive step are all answerable only by trusting whoever built it. An attempt to manipulate the agent through a planted instruction meets no independent check, because every check depends on output the model itself produced.

11 · Components, and why

What each component does, and why it was chosen over the alternatives

Everything here is under a permissive open-source licence, meaning it can be used commercially without obligation. That was a hard requirement, and it ruled out several otherwise strong options.

Storage, control and policy

ComponentWhat it does hereWhy this one
SeaweedFSStores the actual data files, the default storage backendIt supports credentials limited to one folder, or to one organisation's own bucket, which is how a sensitivity level becomes a physical restriction rather than a rule the application is trusted to apply. Every organisation's ordinary ingest and agent-upload writes go through that organisation's own standing identity, never a shared admin key. TemporalRuns long jobs: the pipeline, imports and agent runsIt records the state of a job durably, so retries, timeouts and resuming after a crash are provable behaviour, not a description of intent. This is what lets an agent pause for days awaiting approval.

cryptography (Python)Encrypts individual records and stored credentialsIt is the standard, well-reviewed Python library for this, and using a per-record key is what allows permanent deletion without altering any locked dataset.

Design patterns used

  • Rules as testable code, not as instructions to the model. Access decisions are evaluated by the policy engine against an assigned identity. The AI model is never asked to respect a rule, because anything it is asked can also be argued out of it.
  • Human approval built into the structure. The pause before a significant action is part of how the agent is defined, so it cannot be skipped by the model deciding it is unnecessary.
  • Durable execution. A paused agent run is stored, not held in memory, so an approval that arrives days later resumes the run without repeating the work already done.
  • Versioning code by its content, the same way data is versioned. An agent version is identified by the exact source it was built from, which is the approach MLflow and LangSmith take for tracking models and prompts.
  • Several detectors instead of one. Three detection methods that fail differently are combined, because relying on a single model means inheriting every category it happens to be weak at.
  • Layered defence against prompt injection. The agent's identity is held outside the model, permissions are rechecked on every single action, and every attempt is recorded. An injected instruction therefore has nothing to escalate into and no way to hide the attempt.
  • Identity comes from a session, never from a request body. Every endpoint that approves, rejects or revokes something reads who is asking from a session Kratos issued, never from a field the caller filled in.
  • Credential minting isolated per storage backend, and never handed to untrusted code. Each storage backend has its own module that knows how to mint a short-lived, scoped credential; a sandboxed agent never receives one directly; it can only trigger a copy the trusted worker fetches on its behalf.

What to keep in mind before doing it

  • Some swaps are almost free, others are a rewrite. Storage and the database change by configuration alone, because the interfaces match. Replacing Temporal or the policy engine with a cloud-specific equivalent means rewriting how jobs and rules are expressed, which is real work.
  • Keeping PostgreSQL matters more than it looks. Several guarantees, including locked datasets and refusing writes to a closed account, are enforced by the database itself. A managed PostgreSQL service preserves them. Moving to a different kind of database would mean rebuilding those protections in application code, where they are easier to bypass.
  • Using a hosted AI model changes what you can process. Running the model locally means no data leaves the organisation. Sending prompts to a hosted model may be fine for some data and prohibited for other data, and that decision usually belongs to legal and compliance rather than engineering.
  • Cloud access controls do not replace this system's. Cloud identity services decide who may reach a service. They do not record why a particular person was granted a particular dataset for a particular purpose, which is the question this platform exists to answer.
  • Staying portable is an option. Every component here also runs on a cloud provider's plain virtual machines or container service. That keeps the system movable between providers, at the cost of operating it yourself instead of consuming a managed service.
