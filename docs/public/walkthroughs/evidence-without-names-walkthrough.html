Words used on this page

Organisation
A company or hospital group that uses Munitas. Each organisation sees only its own data.
Dataset
A named collection of records, such as a table of patient admissions.
Locked column
A column whose values are scrambled under a key made for each person. Reading them back needs permission. Destroying a person’s key later makes their values unreadable for good, while the sealed table itself never changes.
Person code
A label that stands for one person and means nothing on its own. It replaces the number that identified them.
Privacy auditor
A person who checks how locked data was used. The role reads records of use and no personal data.
Data protection officer
A person who watches how an organisation handles personal data. The role decides nothing about who may read it.
Privacy contract
A file that says, column by column, how identifying each column of a table is and what is done to it when the table is sealed, and how to find the person each row is about.
Version
One sealed state of a dataset. Changing the contents means making a new version, never editing an old one.
Role
A named set of permissions that a person can hold, such as the permission to decide who may read a department’s data.
Lease
Permission, given by the custodian, to read one dataset for one stated purpose and for a limited time.
Sealed
Finished and closed for good, so that it can never be edited.
Pipeline
A series of steps that Munitas runs on a dataset version, each step after the ones it depends on. The last step is a gate decision.

PART ONE

The auditor checks how locked data was used, and sees no name

A privacy auditor is a person who checks how locked data was used. The role reads records of use and no personal data. Everything that happens to locked data leaves a record, and this page is where those records can be read together.

1
Marlow
Marlow reads who read locked data, and who was refused
Munitas console · Locked data audit · /locking-audit

Marlow holds the privacy auditor role. The page lists every read of locked columns and every opening of locked files, every refusal, every permission with who asked and who decided, and what was done to each column. People appear by name. No name of a patient and no value from any table appears at all.

The page says No person's name and no value from any table appears here. Under Who read locked columns, and who was refused, Devi appears with Read and with Refused for clinic-appointments, version 1, and the reason for the read is Devi's own, to see what the postcode column really holds before I write the rule that locks it.
2
Marlow
Marlow sees what was done to every column
Munitas console · Locked data audit · How each table's columns were treated

For each table sealed under a privacy contract, the page lists its columns, how identifying each is, and what was done to it, so an auditor can check that what the contract promised is what happened.

patient_name and reason_for_visit say Locked under the person's key, and patient_number says Replaced by a person code.
3
Marlow
Marlow sees every key that was opened, and why, and finds one person in two places
Munitas console · Locked data audit · Keys

Each patient has a key of their own. It was made when the patient first appeared, and it is opened when their locked values or files are read. The list shows each opening with the time, who did it, why, and a person code, which stands for one patient and means nothing on its own. The pipeline's openings of the recordings appear beside Devi's reading of the table. The same person code appears on lines about the table and on lines about a recording, which is how Munitas shows that the patient in the recording and the patient in the table are one person with one key. A script checked this.

Each line reads A key was opened, and under it gives the reason, such as To read locked rows, under a lease or To open a locked file in the page, with an approver's permission. Each line also shows who opened the key and a person code that begins with T-. The lines for the pipeline's run name the run, with a code that starts pipeline_run or action_run, and give the reason For a pipeline run.
4
Nakamura
The data protection officer reads the same record
Munitas console · Locked data audit · /locking-audit

Nakamura is the data protection officer, a person who watches how the organisation handles personal data. The same page is open to that role, with the same limit: it shows how locked data was used and never what the locked data says. A script checked that none of the three patients' names appears anywhere on it.

The signed-in person at the foot of the menu is Nakamura, Data protection officer. The page is the same one, and its first lines are under Who read locked columns, and who was refused.
