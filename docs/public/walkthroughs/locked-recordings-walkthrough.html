Words used on this page

Organisation
A company or hospital group that uses Munitas. Each organisation sees only its own data.
Department
A team inside an organisation that owns some of its data, such as Cardiology.
Dataset
A named collection of records, such as a table of patient admissions.
Sealed
Finished and closed for good, so that it can never be edited.
Version
One sealed state of a dataset. Changing the contents means making a new version, never editing an old one.
Locked recording
A recording stored scrambled under a key made for the one patient it is about. Reading it back needs the platform to open it, and destroying the patient’s key later makes it unreadable for good.
Manifest of recordings
A small table, saved as a CSV file, with two columns: the recording and the patient it is about. It is how the platform knows whose key to lock each recording under.
Answer key
A file that holds the correct written text of one recording, used to check how well names were removed from it. It is named after its recording and belongs to the same patient.

PART ONE

Devi brings in recordings so that one person can be erased later

A dataset is a named collection of data that belongs to one department, the team inside an organisation that owns some of its data. A recording of a consultation is about one person, and a person may later ask to be erased. This part shows how recordings are brought in so that erasing one person is possible: each recording is locked under a key made for the person it is about, and destroying that key makes everything locked under it unreadable for good.

1
Devi
Devi is asked whether anyone will ever need to be erased from this data
Munitas console · Bring data into a dataset · /datasets/<id>/ingest

Devi is a data engineer in the Cardiology department of the Health organisation, a role that may bring data in. A dataset for consultation recordings is already registered and still empty. Before any file can be added, the page asks one question: will anyone ever need to erase one person from this data? The answer has to be given now, because locking cannot be added after the upload. The first choice, which is selected when the page opens, stores the files exactly as they are, and nothing in them is locked.

A box titled Will you ever need to erase one person from this data? has two choices. No. Store the files as they are. is selected, and the usual Upload files area is below it, with the button Seal this as version 1 greyed out. Sealing finishes a version, which is one state of a dataset, so that nothing can be added to it afterwards.
2
Devi
Devi answers yes, and says the data is recordings
Munitas console · Bring data into a dataset · /datasets/<id>/ingest

Devi answers yes. The page explains what that means: the data of each person is locked under a key made for that person. Locking scrambles the data, so that nothing can read it without the key. Erasing a person destroys their key, so what was locked for them can never be read again, and the rest of the data stays. The page also says, in the same place, that locked data is hidden and not anonymised: it is still personal data until the person is erased. Devi then says what is being brought in. The other choice is a table of records. Here it is recordings, which are audio files with one person in each, so the upload area is replaced by a way to name the person of each recording.

Yes. Lock what identifies a person, with one key for each person. is selected, and the sentence Locked data is hidden, not anonymised is on the screen. Under What are you bringing in?, Recordings, one person in each is selected. Three boxes follow: the kind of identifier that names a person, the manifest, which is the list that says which person each recording is about, and the recordings themselves.
3
Devi
A manifest and files with mistakes are refused, with every mistake listed
Munitas console · Bring data into a dataset · /datasets/<id>/ingest

Devi types the kind of identifier that names a person, a hospital chart number. Devi then chooses a manifest, which is a small table saved as a CSV file with two columns, the recording and the person it is about, and three files with several mistakes in them. The page checks the manifest against the files straight away, before a single byte is sent, and lists every problem at once, so one look shows all of them. One of the files is an answer key. An answer key is a file that holds the correct written text of a recording, used later to check how well names were removed from it. It is named after its recording and belongs to the same person.

A yellow box titled Fix these before uploading: lists four problems, one on each line. They name visit-2.wav, which names no person, visit-4.wav, which is not in the manifest, visit-9.truth.json, an answer key whose recording is missing, and visit-3.wav, which is in the manifest although the file was not chosen. The button Upload and lock is greyed out.
4
Devi
With the right manifest and files, the upload is allowed
Munitas console · Bring data into a dataset · /datasets/<id>/ingest

Devi corrects the manifest and chooses the right files: two recordings, each with its own person named in the manifest, which is the table that says which person each recording is about, and the answer key of the first recording. Nothing is left to list, and the button that starts the upload can be pressed. The chart numbers in the manifest are invented, and the recordings are noise, so that nothing of a real person is in them.

The yellow box has gone. The button Upload and lock is now blue. The boxes read manifest.csv and 3 files.
5
Devi
Each file is sent in parts and locked under the key of the person it is about as it arrives
Munitas console · Bring data into a dataset · /datasets/<id>/ingest

Pressing Upload and lock sends each file to the platform in parts of at most 8 megabytes. A key is a secret value that locks and unlocks data, and locking scrambles the data so that it cannot be read without the key. Each part is locked under the key of the person it is about as it arrives, so a plain copy of a recording is never stored. The platform finds the person from the identifier, makes a key for any person it has not met before, and does not keep the identifier itself. A part that fails because the connection did is sent again by itself, and a connection that stays down pauses the upload and keeps what was already sent, so carrying on sends only the rest.

Three rows, visit-1.wav, visit-2.wav and visit-1.truth.json, each have a full green bar and end with Locked. A new button, Seal these recordings, appears below them.
6
Devi
Devi seals the recordings
Munitas console · Bring data into a dataset · /datasets/<id>/ingest

Devi seals the recordings. Sealed means finished and closed for good, so that nothing can be added to it or changed in it afterwards, and later recordings become a new version, which is one sealed state of a dataset. Before it seals, the platform checks that every file was locked, that no ordinary file is mixed in with the locked ones, and that every answer key belongs to the same person as its recording. If any check fails, nothing is sealed, and every reason is listed.

A green box reads Sealed as version 1: 2 recordings about 2 people. It says that each recording is locked under the key of the person it is about, and offers a link, Open this version.
7
Devi
The version says how many recordings and people it holds, and names nobody
Munitas console · Version detail · /versions/<id>

Devi opens the new version, which is the sealed state of the dataset that the upload just made. Under the heading Locked recordings the page counts what it holds and says nothing about who the people are: no identifier and no name from the manifest appears anywhere on it. A pipeline run is a program that runs on a version, and it opens a recording only while it is running, with every opening written to a record that names the run. When a person is erased later, their recordings are counted here as unreadable, and every later run leaves them out.

Locked recordings shows three counts: Recordings 2, People 2 and Unreadable because the person was erased 0. The line below says that every opening is recorded with the run named.
