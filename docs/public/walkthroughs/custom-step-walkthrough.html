Health organisation · Cardiology

Let your own code read recordings and write files, with an approver

A data engineer uploads a pipeline with a step of their own that reads recordings and writes files. Because that step is code the platform did not write, the platform refuses to run the pipeline until an approver of the owning department, who did not upload it, approves it. The run then reads the recordings only through the platform, and the files it writes become a new version that waits for a review and records exactly what made it.

How to read this page

  • Screenshots are real pictures of the Munitas console, the web app that people open in a browser. Click any picture to enlarge it.

Words used on this page

Organisation
A company or hospital group that uses Munitas. Each organisation sees only its own data.
Department
A team inside an organisation that owns some of its data, such as Cardiology.
Dataset
A named collection of records, such as a table of patient admissions.
Custodian
A person who holds the data custodian role, which allows deciding who may read data. A custodian decides for the departments they are an approver for.
Department approver
A custodian who is listed for one department and may approve access to its data and confirm claims about it. A department can have several, and any one of them can act on their own.
Sealed
Finished and closed for good, so that it can never be edited.
Version
One sealed state of a dataset. Changing the contents means making a new version, never editing an old one.
Pipeline
A series of steps that Munitas runs on a dataset version, each step after the ones it depends on. The last step is a gate decision.
Run
One execution of an agent or a pipeline, started for a stated purpose.
Custom step
A step of a pipeline whose script was written by the person who registered the pipeline, instead of one of the steps Munitas provides. It runs in a closed container with no internet, no key and no storage address, and can only ask the platform for the recordings it is allowed to read and send back the files it makes.
Under review
The access level of something that no person has reviewed. Nobody may use it until a reviewer decides that it may be released.
Fingerprint
A value worked out from the exact contents of a file. It changes if even one byte changes, so it shows that a file was not altered.

PART ONE

Devi uploads a pipeline with a step of their own, and is stopped

A pipeline is a series of steps that Munitas runs on a version of a dataset. Most steps are provided by Munitas. A custom step is one whose script was written by the person who registered the pipeline. A step like that is code that the platform did not write, so when it asks to read recordings or to write files, a second person has to agree first. This part shows Devi uploading such a pipeline and the platform refusing to run it.

1
Devi
Devi uploads a pipeline whose step reads the recordings and writes files
Munitas console · Pipeline detail · /pipelines/<id>

Devi is a data engineer in the Cardiology department of the Health organisation. A department is the team inside an organisation that owns some of its data. Devi has registered a pipeline called silence-the-start, and now uploads its first version, which is one sealed state of the pipeline that can never be edited. The version is made of a YAML file, which is a plain text file that names each step, and a zip file that holds the script of each step. The first step is a custom step. The YAML file says that the step is given the recordings and may write files, and its script makes the first half second of each recording silent and writes the result back.

Two files are chosen, pipeline.yaml and scripts.zip, and the button Upload version is blue. Above the form the page says Owned by Cardiology. Registered by Devi. and No versions.
2
Devi
The version is sealed, and it waits for an approver
Munitas console · Pipeline detail · /pipelines/<id>

Uploading seals the version. Sealed means finished and closed for good, so that it can never be edited, only replaced by a next version. The page lists the two steps and then shows a yellow box. The box says that the first step is given the recordings, so code that the platform did not write reads the sound, and that it writes files, which become a version that waits for a person’s review. A version like this cannot run until an approver of the owning department approves it, and the approver cannot be the person who uploaded it. An approver is a data custodian, a person who may decide who reads a department’s data, who is listed for that department.

Under v1 the line silence (script: steps/silence.py, given the recordings, writes files) and the line decide (gate) ← silence are listed. A gate is the last step of a pipeline, where a person decides whether the result may be released. A yellow box says the version cannot run until an approver of Cardiology, who is not Devi, approves it. There is no approve button on Devi’s screen.
3
Devi
Devi tries to run it, and is refused
Munitas console · Version detail · /versions/<id>

Devi opens the version of the recordings that was sealed, which means finished and closed for good, and chooses the new pipeline in the list of pipelines that can be run on it. The platform checks before it starts anything, and refuses. It does not wait until the step reads a recording to find out, and nothing is left behind: no run, no file and no record of an attempt to read.

A red box reads Nothing was started. Fix these first: and says that the version lets the custom step silence read the recordings or write files and has not been approved, and that an approver of the department that owns the pipeline, who is not the person who uploaded it, approves it first.
PART TWO

Hartley approves it

The approval is a decision by the department that owns the pipeline, made by a person other than the one who uploaded the version. It is recorded with who gave it and when, and it can be taken back.

4
Hartley
Hartley, an approver of Cardiology, is offered the approval
Munitas console · Pipeline detail · /pipelines/<id>

Hartley is the data custodian for Cardiology. Hartley opens the same page and sees the same yellow box, and this time it has a button, because Hartley is an approver of the department that owns the pipeline and did not upload the version. Approving is the department’s statement that the script has been looked at and may be given the recordings and may write files.

The screen names Hartley and Data custodian for Cardiology. The yellow box is the same as on Devi’s screen, with one addition, a button Approve this version.
5
Hartley
Hartley approves it, and can take the approval back at any time
Munitas console · Pipeline detail · /pipelines/<id>

Hartley presses the button, and the approval is recorded. Taking it back stops a step that is already running at its next request, because the platform checks the approval again on every request that the step makes and not only when the run starts.

The yellow box now begins Approved by Hartley on followed by the date and time, and the button has become Take the approval back.
PART THREE

Devi runs it, and finds what it made

With the approval in place the same run starts. This part shows what the run records and where the files that the step wrote end up.

6
Devi
Devi runs the pipeline, and the run names the version it made
Munitas console · Pipeline run · /pipeline-runs/<id>

Devi starts the same run again, and this time it works. The script runs in a container, which is an isolated environment. This one has no internet, runs as a user without special rights, and holds no key and no storage address. It can only ask the platform for the recordings it is allowed to read, and send back the files it makes, and the platform checks the approval on every request. When the script ends, the platform seals the files it finished, which closes them for good, as one new version, and the page of the run links to it.

Under Steps the step silence reads Done and has a link Open the version it made. The step decide is also Done.
7
Devi
The new version is under review, so nobody can use it yet
Munitas console · Version detail · /versions/<id>

Devi follows the link. The files are in a new dataset, a named collection of data, whose name is the name of the first dataset followed by the name of the step. The version is marked Under review, the access level of something that no person has reviewed. Nobody may use it until a reviewer decides. The platform made this version itself from what the script sent, so the script was never given any way to write into storage. The page also says that the version is stored as a table of 2 rows, one for each file it holds.

The title ends with -silence v1. Both Access level when sealed and Access level now read Under review, and Records is 2.
8
Devi
The version records exactly what made it, and what it was made from
Munitas console · Version detail · /versions/<id>

Further down the same page, Where this came from names what produced the version: the step, the identity that the platform runs pipelines as, the code version and the environment. The code version is a fingerprint of the exact pipeline version that was approved. A fingerprint is a value worked out from the exact contents of a file, so it changes if the contents change. Made from links to the version of recordings that the step read, so erasing a patient later lists this version among what was made from their recordings.

Step reads custom_step, Run by reads health-pipeline, and Code version starts 78e344ac5074f4, the same start as the fingerprint of the approved version in the second step. Made from is a link to the version of recordings.
